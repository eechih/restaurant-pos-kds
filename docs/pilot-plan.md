# 試營運計畫

- **目標：** 讓真實店家試營運
- **決定日期：** 2026-11-05

功能的優先順序以「店家能不能每天順利營業」為準，展示效果其次。

| 批次 | 內容 | 狀態 |
|---|---|---|
| 1. 減少現場出錯 | 售完切換、新單音效、取消品項同步給顧客 | 已完成 |
| 2. 店家能自己管理 | 菜單管理後台、員工角色權限 | 已完成 |
| 3. 提高營收 | 銷售報表，再來是推薦與促銷 | 未開始 |
| 4. 正式營業前 | 線上付款、電子發票、退款紀錄、AWS WAF | 未開始 |

如果試營運就會實際退款，退款紀錄要提前到批次 2。

顧客掃碼點餐的設計見[顧客掃碼點餐](qr-ordering.md)。

## 第 1 批的設計

- **售完切換：** 員工在 `#/pos/availability` 切換，不需要改後端權限。其他裝置和顧客的菜單最多 1 分鐘內更新；在那之前下單會被後端拒絕，所以不會賣出已售完的品項。
- **新單音效：** POS 提示新的待收款訂單，KDS 提示新的工作單。瀏覽器規定使用者操作過頁面才能發聲，所以開啟頁面後要先點一下畫面，未解鎖時頂端會顯示提示。員工代客點餐會立刻收款，不會觸發提示。
- **取消品項同步：** 顧客的訂單頁會劃掉已取消的品項，並提示到櫃台退款。訂單上菜後，狀態改為每 30 秒更新一次，所以用餐後的取消也看得到。

## 第 2 批的設計

### 角色

只分**店長**和**員工**兩種，店長是 Cognito 群組 `MANAGER` 的成員。

| 誰 | 可以做的事 |
|---|---|
| 員工 | 開桌、點餐、收款、取消品項、清桌、操作 KDS、售完切換、列印 QR Code |
| 店長 | 員工能做的事，加上修改菜單、桌位、重新產生 QR Code、管理員工帳號 |

- **廚房不另分角色：** KDS 上只能改製作狀態，不涉及金額。
- **取消品項仍開放給員工：** 現場需要立刻處理。批次 4 有退款紀錄後，再評估是否改成店長核准。
- **售完切換不經過菜單權限：** 員工改用 `setItemAvailable`，它只寫 `available` 一個欄位，`MenuItem` 的其他欄位只有店長能改。
- **前端只負責顯示：** 員工看不到店務設定和「重新產生」，但真正的限制在後端，直接呼叫 API 也會被拒絕。

### 菜單與桌位（`#/pos/settings`）

- **改價格：** 已點的單維持原價，因為工作單存的是點餐當下的快照。顧客購物車裡的舊價格會被 `PRICE_CHANGED` 拒絕，畫面會請顧客確認新金額。
- **刪除品項：** 不影響已點的單。只是當天賣完應該用售完，隔天才能直接恢復，刪除對話框也會提醒。
- **不會互相覆蓋：** 儲存品項不會寫入售完狀態，儲存桌位不會寫入 QR token，所以編輯畫面開著時，其他人做的售完切換或重新產生不會被蓋掉。
- **分類：** 裡面還有品項時不能刪除。
- **桌位：** 新增時自動產生 QR token；改名不影響已印好的 QR Code；用餐中或有待收款訂單的桌子不能刪除，避免付款後找不到桌子。

### 員工帳號（`#/pos/settings/staff`）

- **邀請：** 店長輸入 Email，Cognito 寄出臨時密碼，7 天內要登入並設定新密碼，過期可以重寄。邀請信不含網址，要另外告訴員工。
- **不能鎖住自己：** 店長不能變更自己的角色，也不能停用自己，所以至少會留下一位店長。
- **只停用、不刪除：** 離職員工停用即可，之後要回來也能重新啟用。
- **生效時間：** 升為店長後，對方重新整理頁面就會生效，因為 App 開啟時會更新登入憑證。取消店長或停用時，Lambda 會撤銷對方所有裝置的登入；App 下次更新憑證時發現已撤銷就會登出。但 AppSync 只檢查 access token 的簽章和期限，所以已開啟的畫面最長 1 小時內仍能用舊權限操作。要縮短可以調低 access token 的有效期限。
- **寄信上限：** 使用 Cognito 內建的寄件服務，每天約 50 封，試營運足夠。正式營業前應改用 Amazon SES。

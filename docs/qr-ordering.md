# 顧客掃碼點餐

- **狀態：** 已決定，分階段實作中（見[階段](#階段)）
- **決定日期：** 2026-11-05

## 決定

顧客掃描桌上的 QR Code 自行點餐，**付款成功後廚房才開始製作**。這取代現有的內用後付流程。

| 問題 | 決定 | 原因 |
|---|---|---|
| 付款方式 | 先做櫃台付款，之後再加線上付款 | 兩者共用同一套訂單狀態；櫃台付款不需要金流帳號，可以先驗證整個流程 |
| 同桌多人 | 每支手機各自下單、各自付款 | 共用購物車需要即時同步。缺點是同桌顧客無法合併結帳 |
| 員工代客點餐 | 同樣先付款才送廚 | 保留後付流程就要長期維護兩套帳務邏輯 |

## 流程

```
掃碼 → 看菜單 → 購物車 → 下單 ──────────→ 付款成功 ──→ KDS 製作
                         │ 伺服器重算金額     │ 同一筆交易建立 KitchenTicket
                         └ Order: PENDING     └ Order: PAID
                                  └ 逾時未付 → EXPIRED，廚房不會看到
```

**核心規則：付款成功後，後端才建立 `KitchenTicket`。** KDS 只看得到已付款的單，所以不需要判斷付款狀態。

## 信任邊界

顧客是不可信任的使用者，他們的裝置傳來的任何資料都可能被竄改。

| 角色 | 可以做的事 |
|---|---|
| 顧客（未登入） | 讀菜單與促銷、用 token 查桌名、呼叫 `placeOrder`、用訂單 ID 查自己的訂單 |
| 員工（已登入） | 確認櫃台收款、操作 KDS、管理桌況、切換售完 |
| 店長（`MANAGER` 群組） | 員工能做的事，加上修改菜單、桌位、QR Code 和員工帳號 |
| 後端 Lambda | 計價、建立訂單、建立 `KitchenTicket` |

規則如下：

- **`placeOrder` 不接受價格：** 顧客只送品項和選項 ID，金額由 Lambda 依菜單和促銷計算。
- **顧客不能直接存取營運資料：** 不對訪客開放 `KitchenTicket`、`GuestCheck`、`Seating`、`Order` 的讀寫，也不開放列出訂單。
- **QR Code 放隨機 token，不放 `tableId`：** `table-A1` 很容易被猜到。訪客不能讀取 token 欄位，否則可以冒用其他桌。
- **訂單 ID 不可猜測：** 顧客查單靠的是持有訂單 ID。

未付款的單不會進廚房，所以惡意下單最多留下會過期的訂單。

顧客的權限同時開放給 `allow.guest()` 和 `allow.authenticated('identityPool')`。已登入員工的裝置開 QR 連結時，身分池給的是已驗證身分而不是訪客，少了後者就會被拒絕。

## 資料模型

`Order` 只由 `orders` Lambda 寫入，員工只能讀取（`amplify/data/resource.ts`）。

| 模型或函式 | 變更 |
|---|---|
| `Order` | 新增。下單時凍結品項和金額，付款後才有 `checkId`。儲存的狀態只有 `PENDING`、`PAID` |
| `GuestCheck` | 代表「這桌這次用餐」，付款狀態移到 `Order`。`guestCount` 改為選填，因為顧客的第一筆付款也可能開桌 |
| `tableState` | 只分 `EMPTY`、`DINING`。有 `Seating` 就是用餐中，由員工清桌 |
| `KitchenTicket` | 內容不變，只由 Lambda 建立，ID 由 `orderId` 推導。員工只能更新狀態 |
| `LineVoid` | 付款後取消品項會顯示在顧客的訂單頁，並提示到櫃台退款；第 4 階段才連動退款 |
| `MenuItem` | 新增 `available`（售完），員工在 `#/pos/availability` 透過 `setItemAvailable` 切換，其他欄位只有店長能改。`featured` 留到第 5 階段 |
| `DiningTable` | 新增 `qrToken`，訪客不可讀。ID 為 `takeout` 的那筆是外帶入口，不是桌位 |

## 關鍵規則

- **付款確認是一筆交易：** Lambda 用 DynamoDB 交易同時更新訂單、建立工作單，必要時開桌。重試會看到已付款的訂單，直接回傳結果，不會多一張單。
- **兩筆付款同時開桌：** 較慢的交易會失敗，重試後會加入先開的那張帳單。
- **金額在下單時凍結：** 前端送 `expectedTotal`，和伺服器算的不同就以 `PRICE_CHANGED` 拒絕。購物車顯示的只是預估價。
- **訂單 15 分鐘後逾時：** `EXPIRED` 由 `expiresAt` 推算，不需要排程工作。逾時的訂單不能付款。
- **每桌未付款訂單上限 10 筆：** 超過就以 `TOO_MANY_PENDING` 拒絕顧客下單。付款或逾時後就會恢復。員工代客點餐不受限，有人灌單時櫃台仍能接單。索引是最終一致的，短時間連發可能略微超過。
- **售完由後端檢查：** `placeOrder` 會拒絕 `available` 為 false 的品項。
- **顧客查單用輪詢：** 第一版不需要 `useLiveState`，用 TanStack Query 的 `refetchInterval` 即可。

### 為什麼員工端另外訂閱

Lambda 直接寫入 DynamoDB，模型的訂閱看不到這些變更，所以員工端改訂閱 `onOrderPlaced` 和 `onOrderPaid`。實作時要注意兩點：

- **通知直接帶完整資料：** 透過 data API 讀回是最終一致的，可能讀不到交易剛寫入的資料，實測曾造成帳單少一輪。
- **訂閱端要檢查內容：** 失敗的 mutation 也會推播空結果，而欄位由呼叫者決定。顧客能呼叫 `placeOrder`，所以不能相信這些內容。被略過的通知由每分鐘的重新同步補上。

## 前端結構

顧客端和員工端共用一個網站和同一套路由，但彼此隔離：

- **登入：** 員工路由在 `Authenticator` 內；顧客路由（`#/order/$tableToken`、`#/order/$tableToken/$orderId`）在外，不需要登入。
- **載入：** 員工端的程式碼（Amplify 登入介面、`useLiveState`）按需載入，顧客不會下載。
- **資料存取：** 顧客端用獨立的 `CustomerRepository`，拿不到 `clearTable` 這類員工方法。
- **Demo 模式：** 同樣提供 demo 實作，以本地模擬付款。它無法展示信任邊界，因為所有資料都在瀏覽器裡。
- **櫃台對單：** 訂單編號是訂單 ID 的前 4 碼（`orderCode`），顧客頁和 POS 的待收款都會顯示。它只用來對單，不是憑證。
- **購物車：** 存在顧客裝置的 `localStorage`，重新整理不會消失。金額由目前的菜單計算，只是預估。
- **QR Code：** 員工在 `#/pos/qr` 檢視和列印。重新產生會讓舊的 QR Code 立刻失效。

導入方式見[前端架構擴展方向](frontend-architecture.md)。

## 這個設計解決的已知限制

README 列出的兩項限制在顧客下單流程中不再存在：

- **結帳和送廚的競爭：** 每筆訂單各自付款後才送廚。
- **伺服器不驗算金額：** 金額改由伺服器計算。

## 尚未處理

- **頻率限制：** 每桌上限只防止待收款清單被灌爆。它擋不了大量請求和因此產生的 AWS 費用，公開上線前應再加 AWS WAF。
- **逾時訂單：** 會留在資料庫裡，沒有自動清除。
- **退款紀錄：** 取消已付款品項時只提示手動退款，沒有留下退款紀錄。
- **需要 HTTPS：** 購物車和訂單 ID 用 `crypto.randomUUID`，瀏覽器只在 HTTPS 和 localhost 提供，所以不能用區網 IP 在手機上測試。

## 商品功能（第 5 階段）

這些功能都顯示在顧客端，資料要開放訪客讀取。

- **推薦：** 人工挑選，用 `MenuItem.featured` 標記，顯示為虛擬分類分頁。
- **促銷：** 第一版只做單品特價，用 `Promotion` 模型記錄固定特價和期間。固定價可以避免百分比折扣的四捨五入問題；多個促銷重疊時取最低價，折扣只作用於基本價，不含加料。價格由 `placeOrder` 計算。`TicketLine` 新增選填的 `listPrice` 和 `promotionName`。寫入權限只開放給店長群組。
- **人氣：** 用排程 Lambda 定期彙總近 30 天的銷量，寫入 `ItemPopularity`。不在前端計算，因為 `loadLiveState` 沒有歷史銷售，`LineVoid` 也沒有時間索引。資料太少時隱藏分頁。
- **暫不做：** 滿額折、第二件半價這類整單優惠，等單品特價穩定後再評估。
